● I agree with all four. Here's how I'd write each one into the spec, with one
  pushback on point 3:

  1. Reference date: the "starting after" date is derived from the server's
     nextChargeAt on every render and is never stored. After a skip it moves
     forward by itself.
  2. Skip after a frequency change: no contradiction, and it stays out of the
     limitations. The dialog states two facts: "Your Nov 8 order will be
     skipped. Your next order moves to Dec 8, 30 days later on your current
     schedule. Every 60 days starts after that order."
  3. 409: we never retry automatically. We tell the customer the subscription
     changed elsewhere, show the fresh data, and let them confirm again. Local
     changes are only hidden while the server's status isn't active, not thrown
     away. Pushback: the mock never changes status, so the "hidden while not
     active" rule can only be tested in reducer unit tests, not e2e. I'll say
     that in the spec.
  4. Too much product: two separate buttons. "Skip my Nov 8 order" is the main
     one and "Ship every 60 days" is the second.

  What's still open before I write the specs:

  5. Quantity changes follow the frequency rule. A local quantity change also
     applies "after your Nov 8 order". The next charge keeps the server's
     nextChargeTotalCents, and the page never shows a total the server didn't
     send. The new total per order can be shown as an "after that" line computed
     from unit price × discount. I recommend this because it's the same rule
     everywhere.
  6. "Server dates only" rules out a few things:
     - Pause as a retention offer: a simulated pause needs a pausedUntil date
       the server never sent. I'd drop it. Skip already covers "too much
       product".
     - "Resume now" on the paused fixture: it would need an invented
       nextChargeAt.
     - The date on a local cancel: I'd show "Your subscription is cancelled. You
       won't be charged again." with no date.

     So the paused and cancelled views are read-only: their status, server date,
     products, and a contact-support line.
  7. Status after a simulated cancel: a server status that isn't active always
     wins, and a local cancel can only change the status from active to
     cancelled. That keeps "follow the server" true without letting a refetch
     bring a cancelled subscription back to life.
  8. Offers for the other reasons (no discounts):
     - Costs too much (24%): "Ship every 60 days" first. Its benefit is worked
       out from the server total, e.g. "$X every 60 days instead of every 30".
       Second, "Lower quantity", shown only if an item has quantity > 1. It
       shows the real saving per order from unit price × discount.
     - Trying a different product (15%): swap to a product from catalog. The
       catalog only lists prices before the discount, so the swap shows those
       prices with the same discount applied.
     - Didn't see results (12%) and Other (11%): no offer. Pushing an offer here
       would feel like trapping. "Other" gets an optional text box.
     - Tap count: open cancel → choose a reason → offer screen, which has
       "Cancel subscription" as a plain, always-visible button. That's 3 taps.
       The offer screen also guards against an accidental cancel, so there's no
       separate confirmation step.
  9. Skip from the cancel flow: it closes the cancel flow and opens the same
     skip confirmation dialog. That keeps one code path for slow responses and
     409s, and the customer still sees the exact new date before anything
     happens.
  10. Repeated 409s: the customer can keep confirming, because each try is their
      own choice, not a loop. After the second conflict in a row I'd add "Still
      not working? Contact us" next to the button.

  Spec folders: frequency and quantity editing should be its own feature, so the
