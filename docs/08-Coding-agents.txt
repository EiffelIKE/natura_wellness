  What went into spec.md (SPECS/003-a-plan-changes/spec.md):
  - R1, R2: both controls mark the server's value, as in "Every 30 days
    (current)" and "2 (current)".
  - R2, R3: quantity labels use the full product name, as in "Multivitamin, 30
    tablets quantity".
  - R3: if the server sends no next order date, the text reads "starting after
    your next order", so the page never makes up a date.
  - R5: "Discard changes" only shows while something is pending. Pressing it
    announces "Changes discarded." and moves focus to the "Change your plan"
    heading.
  - R7: if a reload shows the server already has the value the customer picked,
    it's no longer shown as a pending change.
  - R8: the controls live in their own "Change your plan" section after the
    products. The next-order and product sections only show server data.

  How the plan works:
  - Storage: the customer's picks are kept in their own local part of the
    reducer state and never merged into the server data. Each render compares
    them with the latest server data. So "starting after Dec 16" changes to "Jan
    15, 2027" after a skip, and the picks survive a reload after a 409, without
    extra code.
  - Total: "After that" uses the same totalAfterDiscount from
    src/api/fixtures.ts, imported rather than copied, so the rounding matches
    the server. Multivitamin going from 2 to 1 gives $63.67 (6366.5 rounds
    to 6367), which tests the rounding exactly.
  - 002 hooks: 002 left a slot for a pending frequency in the skip dialog. T5
    fills it, and ticks 002's two open criteria (R3 and R11) that were waiting
    on 003.

  Choices I made myself, to check in review:
